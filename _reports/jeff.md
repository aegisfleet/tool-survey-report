# **Jeff 調査レポート**

## **1. 基本情報**

* **ツール名**: Jeff
* **ツールの読み方**: ジェフ
* **開発元**: firelex
* **公式サイト**: [https://github.com/firelex/jeff](https://github.com/firelex/jeff)
* **関連リンク**:
  * GitHub: [https://github.com/firelex/jeff](https://github.com/firelex/jeff)
* **カテゴリ**: AI・機械学習
* **概要**: Qwen3.5やGemma 4をベースにファインチューニングされた、ゼロショット分類用の小規模AIモデル。生成テキストをパースするのではなく、1回のフォワードパスでキャリブレーションされた確率を返すため、非常に高速に動作します。

## **2. 目的と主な利用シーン**

* **解決する課題**: 従来のLLMでは遅すぎる、あるいはパースが必要で不安定だった「自然言語で記述された選択肢からの分類」を、高速かつ正確に行うこと。
* **想定利用者**: ソフトウェア開発者、AIリサーチャー
* **利用シーン**:
  * カスタマーサポートのルーティング（ユーザーの意図分類）
  * モデレーションラベルの付与
  * 音声コマンドの解析
  * ゲームAIの行動決定

## **3. 主要機能**

* **ゼロショット分類**: 事前学習データに含まれない独自のカテゴリであっても、自然言語で状況と選択肢を記述するだけで分類が可能。
* **超高速推論**: 1回のフォワードパスで決定を行うため、RTX PRO 6000で約22ms、Apple M4 Maxで約28msという高速なレスポンスを実現。
* **高いキャリブレーション**: 各選択肢に対する確率と確信度を出力し、結果の信頼性を評価しやすい。
* **複数質問の同時処理**: 1つのリクエストで複数の独立した質問に対して同時に回答を生成可能。
* **容易なファインチューニング**: ドメイン固有のタスクに対して、短時間（1GPUで数時間程度）で独自のファインチューニングモデルを作成可能。

## **4. 動作原理・システム構成**

* **アーキテクチャ**: ローカルファーストのクライアント・サーバー構成（またはライブラリとしての直接組み込み）。
* **主要コンポーネントとデータフロー**:
  * モデル自体はHugging Faceからダウンロード可能な小規模LLM（0.8Bや2Bパラメータ）。
  * サーバープロセス（`jeff-serve`）を起動し、HTTP経由でJSON形式のプロンプトを送信すると、各選択肢の確率が返される。
* **特筆すべき要素技術**:
  * NVIDIA GPU環境では高速カーネルを使用（`cuda` エクストラ）。
  * Apple Silicon環境ではMLXフレームワークを使用（`mac` エクストラ）。
  * テキスト生成を行わず、出力層の確率分布から直接選択肢（A, B, C...）を予測する分類ヘッドを利用。

## **5. 開始手順・セットアップ**

* **前提条件**:
  * Python環境、uvパッケージマネージャ
* **インストール/導入**:

  ```bash
  # CPU
  uv sync --no-default-groups
  # NVIDIA GPU
  uv sync --no-default-groups --extra cuda
  # Apple Silicon
  uv sync --no-default-groups --extra mac

  # モデルのダウンロード
  uv run --no-default-groups hf download mstrasser/Jeff-Qwen3.5-0.8B --local-dir checkpoints/jeff-0.8b
  ```

* **初期設定**:
  * 環境変数 `JEFF_CHECKPOINT` にモデルディレクトリを指定。Apple Siliconの場合は `JEFF_BACKEND=mlx` を設定。
* **クイックスタート**:
  ```bash
  # サーバーの起動
  JEFF_CHECKPOINT=checkpoints/jeff-0.8b PORT=8765 uv run --no-default-groups jeff-serve

  # APIリクエストの実行
  curl -s localhost:8765/v1/systemone -H 'content-type: application/json' -d '{
    "model": "jeff-latest",
    "state": "...",
    "questions": { ... }
  }'
  ```

## **6. 特徴・強み (Pros)**

* **圧倒的なスピード**: 大規模な推論モデル（Jevなど）APIを経由する場合と比較して、ローカルで数十分の一の時間で判断を下せる。
* **ローカル完結によるプライバシーと低コスト**: API料金がかからず、機密データを外部に送信する必要がない。
* **ハードウェア要件の低さ**: 0.8Bモデルであれば1.7GBのVRAMで動作し、一般的なPCでも十分に活用可能。

## **7. 弱み・注意点 (Cons)**

* **複雑な推論は不可**: パラメータ数が少ないため、多段階の論理的推論や計画（プランニング）には向かない。
* **プロンプトへの依存**: 選択肢の「結果」を明確に言語化する必要があり、言い回しによって精度が大きく変わる。
* **日本語への対応不明確**: 英語およびテキストのみ対応（English and text only）と明記されており、日本語での利用は精度低下の可能性がある。

## **12. セキュリティとコンプライアンス**

* **認証**: ローカルでホストするため、APIレベルでの認証機能は提供されていない。必要に応じてリバースプロキシ等で実装する必要がある。
* **データ管理**: すべてのデータ処理はローカルで完結するため、外部へのデータ流出リスクがない。
* **準拠規格**: オープンソースソフトウェアであり、特定のセキュリティ認証は取得していない。

## **13. 操作性 (UI/UX) と学習コスト**

* **UI/UX**: GUIは提供されておらず、CLIおよびAPI経由での利用が基本となる。
* **学習コスト**: JevのAPIフォーマットに慣れている開発者であれば即座に利用可能。モデルのファインチューニングも提供されているスクリプトを用いることで比較的容易に行える。

## **14. ベストプラクティス**

* **効果的な活用法 (Modern Practices)**:
  * プロンプトにおいて、選択肢を短いキーにし、それぞれの行動が何をもたらすかを具体的に記述すること（例：「この動きをすると車にひかれる」）。
  * 複数の独立した質問は1回のリクエストにまとめて送信する。
* **陥りやすい罠 (Antipatterns)**:
  * プランナーとして利用しようとすること。未来の予測（「2ターン後に車が来る」）をさせようとしても、ランダムな選択と同程度の精度にしかならない。
  * 意味のない長いIDを選択肢のキーにすること（処理時間の無駄になる）。

## **18. 総評**

* **総合的な評価**:
  Jeffは「思考するAI」ではなく「瞬時に直感的な判断を下すAI（System 1）」として極めて優秀なツールです。20ms台という速度と数GBのメモリで動作する軽量さは、LLMの応用範囲をゲームのリアルタイムAIや高トラフィックなルーティングなど、レイテンシがシビアな領域にまで広げる可能性を持っています。
* **推奨されるチームやプロジェクト**:
  リアルタイム性を重視するゲーム開発チーム、チャットボットの初期ルーティングを超低遅延で行いたい開発チーム、エッジデバイスでAIによる判断を行いたいプロジェクト。
* **選択時のポイント**:
  判断に必要な情報がプロンプトとして十分に言語化できていること、かつ複雑な論理的推論を必要としないタスクであることが重要です。また、「日本語非対応（English and text only）」とされているため、入力プロンプトや選択肢をあらかじめ英語で構成する等の工夫が必要です。
