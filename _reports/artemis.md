# **ARTEMIS 調査レポート**

## **1. 基本情報**

* **ツール名**: ARTEMIS
* **ツールの読み方**: アルテミス
* **開発元**: Google
* **公式サイト**: [https://github.com/google/artemis](https://github.com/google/artemis)
* **関連リンク**:
  * GitHub: [https://github.com/google/artemis](https://github.com/google/artemis)
* **カテゴリ**: テスト・自動化
* **概要**: ARTEMISは、自然言語の指示を信頼性の高いAndroidの自動化タスクへと変換するAI主導のフレームワークである。エンドツーエンドのワークフロー自動化、ログ収集機能などを備え、各種AIコーディングアシスタントと統合して実機での検証をサポートする。

## **2. 目的と主な利用シーン**

* **解決する課題**: モバイルアプリのテスト自動化において、GUI要素の変更に弱い従来のスクリプトベースのテストや、手動での探索的テストにかかる人的・時間的コストの削減。
* **想定利用者**: モバイルアプリ開発者、QAエンジニア
* **利用シーン**:
  * AIコーディングアシスタント（Antigravity等）を通じた自律的なアプリの動作検証とバグレポートの作成
  * 探索的テストや長時間の安定性テストの自動化
  * 既存の自動テストフレームワーク（pytest等）へのAI駆動検証ステップの組み込み

## **3. 主要機能**

* **自然言語によるデバイス操作**: 自然言語の指示に基づき、Android上の様々なアプリを横断して日常タスクやテストワークフローを実行する。
* **マルチモーダルターゲティング**: 画面上の要素のインデックスに加え、座標ベースや視覚ベースのフォールバックを組み合わせることで、カスタムUIやCanvas、Composeなどにも対応する。
* **IDEとの統合 (MCP Server)**: Model Context Protocol (MCP) を通じて、Antigravity、Claude Code、WindsurfなどのAIアシスタントから実機を操作し、Logcatやスクリーンショットを収集できる。
* **2つの実行プロファイル**: 要件に応じて、高速かつトークン効率の良い「Flash」プロファイルと、計画と検証を伴う探索的な「Pro」プロファイルを使い分けられる。
* **履歴の圧縮と視覚的要約**: 古いスクリーンショットを視覚的な要約に置き換え、完了したステップを検索可能な履歴チャンクに圧縮することでコンテキストを管理する。

## **4. 動作原理・システム構成**

* **アーキテクチャ**: クライアント・サーバー型（デバイスローカルでの実行も含む）
* **主要コンポーネントとデータフロー**:
  * **Artemis Accessibility Helper**: 初回タスク実行時にデバイスにインストールされる軽量なアクセシビリティサービスで、UiAutomationの接続を占有せずに画面レイアウトを読み取る。
  * **Planner & Operator (Proプロファイル)**: PlannerがMarkdown形式のタスクプランを維持し、Operatorが各アクションを実行する。実行前のセーフティネットによる検証や、失敗時の自己修復機能を持つ。
* **特筆すべき要素技術**:
  * **Action Bursts**: プロファイルProにおいて、モデルのターンを待たずに一時的なUI要素（トーストやフェードアウトするコントロールバーなど）に対して連続したアクションを送信する。
  * **Element Locating**: アクセシビリティ階層とOCRを視覚モデルと組み合わせることで、複雑なUIからの要素特定を実現している。

## **5. 開始手順・セットアップ**

* **前提条件**:
  * USBデバッグが有効なAndroidデバイス、またはエミュレータ
  * Python 3.12以上
* **インストール/導入**:

  ```bash
  git clone https://github.com/google/artemis.git
  cd artemis
  ./start.sh
  ```

* **初期設定**:
  * `./start.sh` スクリプトにより、ADB、scrcpy、FFmpeg、Python (`uv`) の依存関係が自動的にインストールされ、MCPサーバーの設定も行われる。
* **クイックスタート**:
  * IDEのチャットプロンプトで「最新の変更をAPKにビルドし、接続されたデバイスにインストールしてテストアカウントでログイン画面を開き、スクリーンショットを返して」のように指示を出す。

## **6. 特徴・強み (Pros)**

* AIによる計画立案から実行、最終的なレポート生成まで、自律的なテストワークフローを実現できる。
* AndroidWorldベンチマークにおいて、20以上のアプリ・100以上のマルチステップタスクで99%以上のタスク完了率を誇る。
* MCP（Model Context Protocol）をネイティブサポートしており、既存のAI開発環境（Cursor、Windsurf等）に容易に組み込める。

## **7. 弱み・注意点 (Cons)**

* 現在はAndroidデバイス・エミュレータのみの対応であり、iOSの自動化には対応していない（ロードマップには含まれている）。
* 初回タスク実行時にAccessibility Helperのインストールによるわずかな遅延が発生する。
* デバイス上での軽量VLMによる完全ローカル実行はまだ実装されていない（ロードマップ予定）。

## **11. エコシステムと連携**

### **11.1 API・外部サービス連携**

* **API**: Python SDKを提供しており、既存のテストフレームワーク（pytestなど）やCI/CDパイプラインに標準的なPythonライブラリとして統合可能。
* **外部サービス連携**: Antigravity, Cursor, Claude Code, Windsurf, VS Code, Cline, Roo Code, OpenClaw などのMCP対応クライアント。

### **11.2 技術スタックとの相性**

| 技術スタック | 相性 | メリット・推奨理由 | 懸念点・注意点 |
|:---|:---:|:---|:---|
| **Python** | ◎ | 公式SDK（`artemis-client`）が提供されており、非同期処理による操作が可能 | 特になし |
| **pytest等のテストフレームワーク** | ◯ | SDKを用いてテストケース内にAI駆動の検証ステップを埋め込める | テスト実行時間が長くなる可能性がある |

## **12. セキュリティとコンプライアンス**

* **認証**: オープンソースツールのため、ツール自体に特定のアカウント認証機能はない。
* **データ管理**: インストールされるAccessibility Helperはローカルデバイス上でのみリッスンし、外部へのデータ送信を行わない設計となっている。
* **準拠規格**: 公式サイトで公開されていない。

## **13. 操作性 (UI/UX) と学習コスト**

* **UI/UX**: WebベースのVisual Test Consoleが提供されており、リアルタイムの画面投影、インタラクティブパネル、推論テレメトリ、アクションの軌跡などを視覚的に確認可能。
* **学習コスト**: 自然言語での指示が可能なため、自動化スクリプトの記述に関する学習コストは低いが、Python SDKを活用した高度な統合にはPythonの知識が必要。

## **14. ベストプラクティス**

* **効果的な活用法 (Modern Practices)**:
  * 日常的・決定論的なUIタスクには「Flash」プロファイルを、探索的テストや長時間の安定性テストには「Pro」プロファイルを利用するなど、目的に応じてプロファイルを使い分ける。
  * `ARTEMIS_HELPER_AUTO_INSTALL` 等の環境変数や事前インストールを活用し、タスク実行時の遅延を減らす。
* **陥りやすい罠 (Antipatterns)**:
  * 長期にわたるタスクでFlashプロファイルを使用し続け、十分な計画や検証が行われないまま操作を進めること。

## **18. 総評**

* **総合的な評価**: ARTEMISは、LLMや視覚モデルを活用してモバイルテストを根底から変革する可能性を秘めた強力なフレームワークである。特にAndroid環境においては、従来の手動テストや煩雑なスクリプトによるテストを大幅に削減できる能力を示している。
* **推奨されるチームやプロジェクト**: Androidアプリを開発しており、E2Eテストの作成やメンテナンスのコストに悩んでいるチーム。AI開発支援ツール（Cursor, Windsurf等）を日常的に使用している開発者。
* **選択時のポイント**: iOSへの対応が必須なプロジェクトでは現時点では採用が難しいが、Androidに特化してテストの自動化と自律化を進めたい場合には非常に有力な選択肢となる。
