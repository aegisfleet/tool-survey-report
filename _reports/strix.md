# **Strix 調査レポート**

## **1. 基本情報**

* **ツール名**: Strix
* **ツールの読み方**: ストリクス
* **開発元**: Strix
* **公式サイト**: [https://strix.ai/](https://strix.ai/)
* **関連リンク**:
  * GitHub: [https://github.com/usestrix/strix](https://github.com/usestrix/strix)
  * ドキュメント: [https://docs.strix.ai/](https://docs.strix.ai/)
* **カテゴリ**: AIペネトレーションテスト
* **概要**: Strixは、本物のハッカーのように振る舞う自律型のAIペネトレーションテストエージェントツールである。動的にコードを実行し、脆弱性を発見した上で、実際に動作するPoC（Proof of Concept）を用いて検証を行う。

## **2. 目的と主な利用シーン**

* **解決する課題**: 手動によるペネトレーションテストの工数削減や、従来の静的解析ツール（SAST）にありがちな誤検知（フォルス・ポジティブ）の削減。
* **想定利用者**: 開発者、セキュリティエンジニア、DevSecOpsチーム
* **利用シーン**:
  * **アプリケーションのセキュリティテスト**: WebアプリケーションやAPIの重大な脆弱性の検出と検証
  * **CI/CDパイプラインへの統合**: プルリクエストごとの自動セキュリティスキャンにより、本番環境への脆弱なコードの混入を防止
  * **バグバウンティの自動化**: バグバウンティプログラムにおけるリサーチの自動化とPoCの生成

## **3. 主要機能**

* **エージェント型ペネトレーションテストツール**: HTTPプロキシ（Caido）、ブラウザ操作、シェル実行、OSINTによる偵察など、ハッカーが使用するツールキットを統合的に活用。
* **複数エージェントのオーケストレーション（Graph of Agents）**: 複数の特化したAIエージェントが連携し、並行してテストを実行。エージェント間で発見を共有し、複雑な攻撃パスを検証する。
* **実際のPoCによる脆弱性検証**: 単なる推測やパターンマッチングではなく、実際に動作するPoC（概念実証）コードを実行して脆弱性を確定させるため、誤検知を極小化。
* **修正コード（PR）の自動生成**: 脆弱性を発見後、安全な修正パッチを自動で生成し、マージ可能なプルリクエスト（PR）として提示する。
* **ローカルWebビューア**: CLI実行時の結果をローカルのダッシュボード（`strix view`）で確認でき、エージェントの動きをライブで可視化可能。
* **コーディングエージェント連携**: Claude Code、Cursor、CodexなどのAIコーディングエージェントにスキルとしてStrixを追加し、エージェント経由でペネトレーションテストを実行可能。

## **4. 動作原理・システム構成**

* **アーキテクチャ**:
  * **OSS版（ローカル）**: Dockerサンドボックス内で動作し、ユーザーが用意したLLMのAPIキーを利用してテストを実行。
  * **Cloud版 / Enterprise版**: Strixが管理するインフラ上で動作し、環境構築不要でクラウドから直接スキャンやPRレビューを実施する。
* **主要コンポーネントとデータフロー**:
  * LiteLLMをバックエンドに使用し、OpenAI, Anthropic, Google Vertex AI, OpenRouter, ローカルLLM（Ollama等）など多様なモデルプロバイダに対応。
  * ローカルのディレクトリを指定した場合、サンドボックス内にリアルタイムでマウントされ、エージェントが実際のコードにアクセス・編集を行う。
* **特筆すべき要素技術**:
  * Pythonサンドボックスを用いてカスタムエクスプロイトを実行。
  * Model Context Protocol (MCP) をサポートし、外部ツールの接続が可能。

## **5. 開始手順・セットアップ**

* **前提条件**:
  * Dockerが起動していること。
  * 対応するLLMプロバイダのAPIキー（OpenAI, Anthropicなど。デフォルト推奨はOpenRouterのZ.ai GLM-5.3）。
* **インストール/導入**:

  ```bash
  # インストールコマンド
  curl -sSL https://strix.ai/install | bash
  ```

* **初期設定**:
  APIキーやモデルの設定を環境変数で行う。
  ```bash
  export STRIX_LLM="openrouter/z-ai/glm-5.3"
  export LLM_API_KEY="your-api-key"
  ```
* **クイックスタート**:
  ローカルのアプリケーションディレクトリをターゲットにスキャンを開始する。
  ```bash
  strix --target ./app-directory
  ```

## **6. 特徴・強み (Pros)**

* **誤検知の少なさ**: 実際にPoCを実行して脆弱性を実証するため、従来の静的解析ツールと比べて開発者の確認負担が圧倒的に少ない。
* **修正までのシームレスな体験**: 問題を見つけるだけでなく、修正コード（PR）まで自動生成するため、修復のライフサイクルが極めて短い。
* **高い拡張性と柔軟性**: オープンソースであり、ローカルでDockerを用いて安全に実行できる。また、多種多様なLLMや、MCPを通じた外部ツールとの連携に対応。
* **CI/CDへの組み込みが容易**: GitHub ActionsなどのCI/CDに容易に組み込め、ヘッドレスモードでの自動実行をサポート。

## **7. 弱み・注意点 (Cons)**

* **LLMAPIコストの発生**: 高度な推論を行うため、ローカル実行であってもLLM（GPT-5.4やClaude Sonnet 4.6など）のAPI利用料がかかる。
* **実行環境の要件**: ローカルで実行する場合はDocker環境が必須となる。
* **テストの安全性**: 強力な攻撃ツールであるため、テスト対象は自身が所有するもの、または明示的な許可を得たシステムに限定する必要がある。
* ドキュメントやUIが主に英語ベースであること。

## **12. セキュリティとコンプライアンス**

* **認証**: Cloud/Enterprise版ではSSO（SAML/OIDC）に対応。
* **データ管理**: Enterprise版ではVPCまたはオンプレミスでのデプロイが可能であり、データソースの保護が可能。また「Zero Data Retention」ポリシーにより、ソースコードがモデルのトレーニングに使用されることはない。
* **準拠規格**: SOC 2 Type II、および ISO 27001 の認証を取得済み。PCI DSSなどに対応したコンプライアンスレポートの出力も可能。

## **13. 操作性 (UI/UX) と学習コスト**

* **UI/UX**: CLIツールとして開発者フレンドリーな設計。さらに、コマンド1つ（`strix view`）でローカルにリッチなWebダッシュボードが立ち上がり、脆弱性の詳細やエージェントの動向を視覚的に把握できる。
* **学習コスト**: 基本的なコマンドはシンプルであり、インストールも容易。各種コーディングエージェント経由での実行も可能なため、開発者の既存のワークフローに自然に溶け込む。

## **14. ベストプラクティス**

* **効果的な活用法 (Modern Practices)**:
  * **スキャンモードの使い分け**: CI/CDパイプラインのPRフックには数分で終わる `quick` モードを使用し、リリース候補版や夜間ビルドにはより徹底的な `deep` モードを使用する。
  * **API仕様書の活用**: OpenAPI/SwaggerやPostmanコレクションファイルをターゲットとして指定することで、クローラーによる探索を省き、API全体を網羅的かつ効率的にテストさせる。
* **陥りやすい罠 (Antipatterns)**:
  * 予算制限（`--max-budget` や `--max-turns`）を設定せずに大規模な対象に `deep` スキャンを実行すると、LLMのAPIコストが想定以上に膨らむ可能性がある。

## **18. 総評**

* **総合的な評価**:
  Strixは、従来の静的解析ツールが抱えていた「大量の誤検知」という課題を、AIエージェントによる「実際の攻撃の試行（PoC）」によって見事に解決している画期的なツールである。さらに、脆弱性の発見に留まらず修正PRまで自動生成する点は、DevSecOpsを推進する上で非常に強力な武器となる。OSSとして提供されており、自身のLLM APIキーを用意すればすぐにローカルで試せる点も高く評価できる。

* **推奨されるチームやプロジェクト**:
  セキュリティ専任担当者が不足している開発チームや、Webアプリケーション、APIの開発においてCI/CDパイプラインを構築済みのDevSecOpsチーム。また、バグバウンティに参加するセキュリティリサーチャーにも推奨できる。

* **選択時のポイント**:
  従来のSAST/DASTツールと競合するものではなく、それらを置き換える、あるいは補完する高度なテスト手法として位置づけられる。運用にあたってはLLMのAPIコストが発生するため、CI/CDで実行する際は `quick` モードを活用し、コスト上限（`--max-budget`）を設定するなどの工夫が必要である。
